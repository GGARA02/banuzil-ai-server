## 3. 데이터 전처리 파이프라인

### 입력 텍스트 형식

```
[성별] {gender} [상황] {situation} [발화] {sentence}
```

성별·상황을 함께 토큰화에 포함하여 모델이 맥락을 학습하도록 설계.

### 카테고리 그룹화

상황 키워드에서 다음과 같이 3개 그룹 자동 분류:

| 그룹 | 분류 키워드 |
|---|---|
| 연애/결혼/출산 | "연애", "결혼", "출산" 포함 |
| 대인관계 | "대인관계" 포함 |
| 기타 | 위 둘에 해당하지 않는 모든 상황 |

이 그룹이 가중치 샘플링·증강의 기준이 된다.

### 가중치 샘플링

학습 데이터에서 그룹별 가중치를 적용해 샘플 수를 조정.
연애/결혼/출산이 실서비스 트래픽의 대다수를 차지하므로 보정한다.

```python
if weight >= 1.0:
    repeat = int(weight)
    extra = int(len(samples) * (weight - repeat))
    result = samples * repeat + random.sample(samples, extra)
else:
    keep = max(1, int(len(samples) * weight))
    result = random.sample(samples, keep)
```

### 텍스트 증강 (`연애/결혼/출산` 한정)

| 기법 | 확률 | 설명 |
|---|---|---|
| 동의어 치환 | 30% | 사전 기반 단어 대체 |
| 무작위 삭제 | 10% | 일부 단어 제거 |
| 인접 교환 | 20% | 두 단어 위치 교환 |

증강 배수(`AUGMENT_MULTIPLIER`)에 따라 원본 데이터의 N배만큼 추가 생성.

## 4. 학습 파라미터 (공통)

| 항목 | 값 | 설명 |
|---|---|---|
| **Max Sequence Length** | 128 | 토크나이저가 자르는 최대 토큰 수. 감성 발화는 짧아 128로 충분. |
| **Epochs** | 5 | 전체 학습 데이터를 5회 반복. Val Cat F1이 가장 높은 시점을 best로 저장. |
| **Train Batch Size** | 32 | 한 번의 가중치 업데이트에 사용할 샘플 수. 클수록 안정·메모리↑. |
| **Eval Batch Size** | 64 | 검증 시 배치 크기. 역전파 없어 메모리 여유로 학습보다 크게 설정. |
| **Optimizer** | AdamW | Adam에 Weight Decay를 올바르게 적용한 버전. 트랜스포머 표준. |
| **Encoder Learning Rate** | 2e-5 | 인코더 가중치 업데이트 속도. 사전학습 가중치 보호용으로 작게. |
| **Head Learning Rate** | 1e-4 (×5) | 분류 헤드 학습률. 새 레이어라 처음부터 학습해야 해서 5배. |
| **Weight Decay** | 0.01 | L2 정규화 강도. 과적합 억제. |
| **Warmup Ratio** | 0.1 | 학습 초반 10% 구간에 학습률을 0→목표값까지 선형 상승. |
| **Dropout** | 0.1 | 학습 중 뉴런 10% 무작위 비활성화. 일반화 향상. |
| **Attention Dropout** | 0.1 | 어텐션 가중치에 적용. 특정 토큰 과의존 방지. |
| **Scheduler** | Linear warmup + Linear decay | Warmup 후 학습률 선형 감소. 후반부 세밀 수렴. |
| **Seed** | 42 | 무작위 요소 고정으로 실험 재현성 보장. |
| **Loss (Category)** | CrossEntropy × 0.6 | 대분류 손실 60% 비중. 더 중요. |
| **Loss (Detail)** | CrossEntropy × 0.4 | 소분류 손실 40% 비중. 58개 클래스 난이도 고려해 낮춤. |
| **Gradient Clip** | 1.0 | 그래디언트 폭주 방지 (Norm 기준). |

### 파라미터 선택 이유 요약

- **인코더 LR을 헤드 LR보다 5배 작게**: 사전학습된 인코더는 이미 한국어 표현을 잘 학습한 상태라 미세조정만 필요. 헤드는 새로 만든 빈 레이어라 빠르게 학습되어야 함.
- **손실 가중치 0.6 / 0.4**: 대분류는 6개 클래스라 학습 난이도 낮음 → 비중 키움. 소분류는 58개라 학습 난이도 높음 → 비중 낮춤. 둘이 1:1이면 소분류가 인코더를 망가뜨릴 수 있음.
- **Max Length 128**: 감성 발화 데이터의 95% 이상이 128 토큰 이내. 더 길게 잡으면 메모리·연산 낭비.

## 5. 모델 아키텍처

세 가지 구조를 실험.

### 5-1. Multi-task (기본 구조)

```
입력: [성별] {gender} [상황] {situation} [발화] {text}
   ↓ Tokenizer (Max 128)
   ↓ KcELECTRA Encoder (12 layers, hidden 768)
   ↓ CLS Token → Dropout(0.1)
   ↓
   ├─→ Category Head (대분류)
   │     Linear(768 → 384) → GELU → Dropout(0.1) → Linear(384 → 6)
   │
   └─→ Detail Head (소분류)
         Linear(768 → 384) → GELU → Dropout(0.1) → Linear(384 → 58)
```

두 head가 같은 인코더를 공유. 손실은 두 head의 CE를 가중합.

```
loss = 0.6 × CE(cat_logits, true_cat) + 0.4 × CE(det_logits, true_det)
```

**적용 버전**: `weighted`, `low_weight`, `unweighted`, `weighted_v2`, `low_weight_v2`, `unweighted_v2`

### 5-2. Hierarchical (계층 구조)

Multi-task와 동일한 아키텍처지만 **소분류 손실에 마스킹** 적용.

```
loss_cat = CE(cat_logits, true_cat)
loss_det = CE(masked_det_logits, true_det)
           ↑ true 대분류에 속하는 10개만 살리고 나머지 -inf
loss = 0.6 × loss_cat + 0.4 × loss_det
```

**추론 시**: 예측된 대분류 기준으로 소분류 logit 마스킹 후 argmax.
→ 대분류-소분류 불일치가 구조적으로 불가능 (예: "기쁨"인데 소분류 "배신당한" 안 나옴)

**적용 버전**: `hierarchical`

### 5-3. Single-task (단일 head)

대분류 또는 소분류 하나만 학습. 인코더 + 단일 head.

```
입력 → KcELECTRA → CLS → Dropout → Head → logits
```

| 버전 | num_labels |
|---|---|
| `category_only` | 6 (대분류 전용) |
| `detail_only` | 58 (소분류 전용) |

해당 태스크에 그래디언트 100% 집중. 단점은 추론 시 두 모델 호출 필요.

## 8. 최종 채택 모델

### 결정

```python
CAT_MODEL_DIR = "models/unweighted_v2"   # 대분류 Top-2
DET_MODEL_DIR = "models/low_weight_v2"   # 소분류 Top-3
```

### 선정 근거

#### 대분류: `unweighted_v2`

| 기준 | unweighted_v2 | 차점자 (category_only) |
|---|---|---|
| 전체 Top1 F1 | **0.6090 ★** | 0.6050 |
| 전체 Top2 Acc | **0.7671 ★** | 0.7585 |
| 연애 Top2 Acc | **0.8106 ★** | 0.8057 |
| 기타 Top1 F1 | **0.6049 ★** | 0.6005 |

전체·연애·기타 모두 우세. category_only가 단일 태스크 집중에도 불구하고 v2의 추가 학습량을 따라잡지 못함.

#### 소분류: `low_weight_v2`

| 기준 | detail_only | low_weight_v2 |
|---|---|---|
| 전체 Top1 F1 | **0.3146** | 0.2736 |
| 전체 Top3 Acc | **0.4931** | 0.4306 |
| 연애 Top1 F1 | 0.3471 | **0.3976** |
| 연애 Top3 Acc | 0.5741 | **0.6045** |

`detail_only`가 전체 1위지만 **연애 구간**에서는 `low_weight_v2`가 명확히 우세.
**서비스 특성상 연애 트래픽이 대다수**이므로 연애 성능을 우선시하여 `low_weight_v2` 채택.

#### 현재 구성 대비 개선폭 (vs unweighted + low_weight)

| 지표 | 기존 | 신규 | 변화 |
|---|---|---|---|
| 대분류 Top2 Acc (전체) | 0.7625 | 0.7671 | +0.0046 |
| 대분류 Top2 Acc (연애) | 0.8067 | 0.8106 | +0.0039 |
| 소분류 Top1 F1 (연애) | 0.3925 | 0.3976 | +0.0051 |
| 소분류 Top3 Acc (연애) | 0.6104 | 0.6045 | -0.0059 |

연애 Top3 Acc가 미세하게 떨어지지만 전체적인 일관성과 대분류 향상으로 트레이드오프 가치 있음.

### 후보로 남길 모델

- `hierarchical` — 단일 모델 운영 시 가장 균형 잡힌 선택지. 대소분류 일관성이 중요한 시나리오에서 우선 고려.
- `detail_only` — 비-연애 도메인 확장 시 소분류 모델 1순위.
